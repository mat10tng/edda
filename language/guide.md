# The Edda guide

Generated by edda guide (tools/guide.py) from Edda's own stories and the
language reference, revision 72. Do not edit it; run edda guide to write
it again. Each passage names its source.

## For agents

### Write the stories from the customer's words

> **Who writes, who reads.** An agent writes level 1 from the customer's
> words. The operator, a person, reads the read view and approves. The
> agent builds level 2 and the code. The checker decides done.
>
> -- reference section 1

> `.edda` is current; the agent edits it.
>
> -- reference section 10

### Never write a .edda.vc

> `.edda.vc` is the file's history: append-only, oldest first, one
> version per approval of a story, an entity block, a role block or a
> function block of that file (role blocks in `glossary.edda.vc`; a
> version of a block of another file is `bad_version`, and a pin sees
> only the versions in the history beside the block's file; a history
> with no function version, as every one before revision 71, stays
> valid); only the operator's approve command, `tools/approve.py`,
> writes it; a repository guard keeps the agent out.
>
> -- reference section 10

> The operator approves a story and the copy is kept. As an operator, I
> want my yes to append the whole story as the next version to the
> history, with the date, my name, one line of because, and a pin on
> every entity and role it names, so that every approved version is kept
> exactly, in order, and the agent cannot write it.
>
> -- story EDDA-005, as the read view says it

> the agent is kept out of the history by a repository guard outside the
> language; that guard, and the history surviving a re-read, are level 2
> and are tested there
>
> -- story EDDA-005, as the read view says it

### Run the check and act on who acts

> **`edda.yaml`** at its root (section 9): the one file that says the
> project uses Edda and how. With it, the tools run on the project:
>
> -- reference section 13

```
<edda>/edda check --root .
<edda>/edda run --root .
<edda>/edda view --root . [STORY ...]
```

> An agent runs the check after each change and acts on each problem's
> `acts`, who must act (decision X, operator decision, 3 Oct 2026); with
> `--json` it reads each problem and its dimensions from one JSON
> document, and the exit code says whether anything was refused or
> failed.
>
> -- reference section 13

> The checker refuses what it cannot read. As an agent, I want every
> fault that stops a file from checking refused, with its file, line and
> one plain message, so that a file that passes has one reading and
> nothing hidden in it.
>
> -- story EDDA-001, as the read view says it

> `acts`: `agent`, the agent fixes it alone; `person`, it needs meaning
> or approval; `language`, the language cannot say it, which is a bug in
> the language.
>
> -- reference section 11

Rules a person acts on, from the table of dimensions (reference section
11): `wider_than_entity`, `computed_cycle`, `contradicting_rows`,
`bad_version`, `bad_pin`, `bad_snapshot`, `pinned_newer`,
`stack_mismatch`, `outside_root`, `unreachable_choice`, `dead_refusal`,
`conflicting_ensure`, `forbidden_change`, `question_on_approved`,
`wording_drift`, `unapproved_link`, `pinned_older`.

### Mark the code that does a story

> The code carries `# <STORY-ID>@<n>`, a comment line of its own
> directly above the top-level function that does an operation of that
> story (above its decorators, when it has any), `n` the story's version
> the code was written against: its newest approved version, or 0 for a
> story never approved. Markers may stand one above the other: one
> function may do operations of several stories.
>
> -- reference section 9

### Done

> **Done.** A story is done when, at its approved version: it is not a
> draft; no pin is stale; every example passes; its operations'
> refusals, ensures, `always` and frame rule hold on the whole suite;
> every link resolves both ways. The checker computes it; the agent
> never marks it. Nothing computes done as one verdict yet.
> `tools/run.py` (section 9) computes two parts for the stories whose
> operations are bound: every example passes, and the operations'
> refusals, ensures, `always` and frame rule hold on every call the
> examples make; it reports that as `examples passed`, never as done.
> The checker's status and link lines give the approved version, stale
> pins and links (section 9); the rules on the host's whole test suite
> are not built.
>
> -- reference section 11

## For people

> A story is a draft until the operator approves it. As an operator, I
> want a story whose body differs from its newest approved version to be
> a draft, whoever changed it, and a refusal or ensure whose wording
> moved away from its meaning flagged, so that nothing the agent writes
> counts until I have said yes.
>
> -- story EDDA-004, as the read view says it

> The operator reads a story as sentences. As an operator, I want a
> story shown as plain sentences in its own order, one per item, with
> the ids hidden, the notes in grey and the questions marked, so that I
> read the business meaning, never the syntax.
>
> -- story EDDA-007, as the read view says it

> The operator sees what changed before saying yes. As an operator, I
> want the difference between the story in the file and its newest
> approved copy as added and removed lines, in order, so that a moved
> rule shows too, so that I read the change, not the whole story, every
> time.
>
> -- story EDDA-006, as the read view says it

> The operator approves with `<edda>/edda approve NAME --by OPERATOR
> --root .` (section 10).
>
> -- reference section 13

> **The pointer line**, one line that tells the host's agents to load
> the guide, printed by `edda guide --pointer [--root HOST]`.
>
> -- reference section 13

> Where it goes is the host's choice: its `CLAUDE.md` or `AGENTS.md`,
> its KB's skill routing, or wherever its agents read first. Edda does
> not place it.
>
> -- reference section 13
